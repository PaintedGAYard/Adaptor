## Entries

### Bug: Missing `CREATE EXTENSION IF NOT EXISTS vector`
> time: [20 09:45] · status: resolved · tags: bugfix, driver, pgvector

`PgVectorDriver.EnsureTableAsync` created tables using `vector`/`sparsevec` types without ensuring the pgvector extension existed.

**Root cause**: No code path called `CREATE EXTENSION IF NOT EXISTS vector`. This must run outside a transaction, but `EnsureTableAsync` receives an already-enlisted connection.

**Fix**: Added `EnsureExtensionAsync()` — opens a separate non-transactional `NpgsqlConnection` and runs `CREATE EXTENSION IF NOT EXISTS vector`. Called at the start of `EnsureTableAsync()`.

**Test**: `PgVectorDriverIntegrationTest.SearchAsync_ShouldCreatePgVectorExtension` verifies the extension is visible to a separate connection after `SearchAsync` triggers initialization.

### Bug: PostgresBlobDriver used nonexistent LO functions
> time: [20 10:00] · status: resolved · tags: bugfix, driver, blob, large-object

`UploadAsync` called `lo_write(@oid, 0, @data)` — this function does not exist in PostgreSQL 17. Same for `lo_read()` in `ReadLargeObjectAsync`.

**Root cause**: PostgreSQL server-side Large Object functions use different names than the client-side (libpq) API. Per PG17 Manual §33.4: server-side functions are `loread` and `lowrite` (no underscore).

**Fix**: Replaced with the correct three-step flow: `lo_open(oid, mode)` → `lowrite(fd, data)` / `loread(fd, len)` → `lo_close(fd)`.

**Note**: Also discovered that the `lo_open` mode constants (`INV_READ` = `0x40000`, `INV_WRITE` = `0x20000`) are actually ignored in PG17+ (the manual says "mode is ignored since 8.1"), so the swapped values in the original code happened to work by accident.

**Files**: `src/Driver/Postgre/PostgresBlobDriver.cs`

### Design issue: Random-access path fd management
> time: [20 10:30] · status: deferred · tags: decision, blob, large-object, placeholder

After fixing the function names, `ReadAsync` (random access) still returned 0 bytes. Investigation revealed that the server-side `lo_open` returns fd = 0 (single descriptor slot per transaction), and the existing code mixed OIDs with fds, causing the read to target the wrong object.

**Decision**: Migrated the random-access path (`OpenAsync`, `ReadAsync`, `WriteAsync`, `SeekAsync`) from `lo_open`/`loread`/`lowrite`/`lo_close` to the simpler `lo_get`/`lo_put` API that works directly with OIDs and doesn't maintain a position cursor. This avoids the fragile fd management entirely.

**Trade-off**: Four operations became no-ops or stubs because `lo_get`/`lo_put` take explicit offset parameters:

| Operation | Design behavior | Current impl |
|---|---|---|
| `CloseAsync` | Release descriptor; subsequent reads fail | no-op |
| `SeekAsync` | Reposition read/write offset | Returns offset but doesn't affect reads |
| `WriteAsync` | Write at current position | Always writes at offset 0 |
| `TruncateAsync` | Shorten blob to given length | no-op stub |

**Deferred to**: pgvector-dotnet refactor cycle (see Future Works).

**Tests**: 4 `[Fact(Skip = "...")]` tests document the designed behavior.

### Bug: OID column type incompatibility
> time: [20 11:30] · status: resolved · tags: bugfix, driver, blob

`reader.GetInt32(0)` on an `oid` column threw `"Reading as 'System.Int32' is not supported for field"`.

**Root cause**: PostgreSQL `oid` is an unsigned 32-bit type; `NpgsqlDataReader.GetInt32()` does not support direct conversion from unsigned.

**Fix**: Replaced with `Convert.ToInt32(reader.GetValue(0))` in all places reading OID columns (both `DownloadAsync` and `OpenAsync`).

### Decision: Test design behavior, not current implementation
> time: [20 12:00] · status: resolved · tags: decision, testing

An early mistake: placeholder tests were written to match the current no-op behavior (e.g., "CloseAsync can be called multiple times and is safe"). User corrected: tests must always assert the **designed** contract. If the implementation doesn't match, mark `[Fact(Skip = "reason")]`.
